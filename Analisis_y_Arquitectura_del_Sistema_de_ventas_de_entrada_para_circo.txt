1. INTRODUCCIÓN EJECUTIVA
================================================================================

El circo necesita un software para vender entradas online evitando que dos 
clientes compren el mismo asiento simultáneamente.

PROBLEMA CRÍTICO:
- Sin protección: 2 usuarios cliquean "Comprar" para asiento A-15 en el mismo segundo
- Resultado esperado: 1 lo compra, 1 recibe "Asiento no disponible"
- Resultado actual (sin sistema): Ambos reciben confirmación (OVERBOOKING)

SOLUCIÓN TÉCNICA:
Usar Optimistic Locking de JPA (@Version) para garantizar que la actualización
de asiento en BD es atómica a nivel de BD.

- Trazabilidad completa: quién, cuándo, qué asiento, resultado

- Cada usuario solo ve sus propias boletas
- JWT para tokens de sesión

5. CONTAINERIZACIÓN CON DOCKER
================================================================================

¿POR QUÉ DOCKERIZAR ESTE PROYECTO?

Este sistema depende de dos piezas que deben funcionar juntas: la aplicación 
Spring Boot y la base de datos MySQL. Sin Docker, cualquier persona que quiera 
correr el proyecto (un recruiter, un compañero, tú mismo en otra PC) necesita 
instalar Java, Maven y MySQL exactamente en las versiones correctas, crear la 
base de datos a mano, configurar usuarios y contraseñas, etc.

Con Docker, todo ese entorno queda empaquetado y se levanta con un solo 
comando, en cualquier sistema operativo, sin instalar nada más que Docker.

QUÉ SE DOCKERIZA EN ESTE PROYECTO:

1. LA APLICACIÓN SPRING BOOT
   Se empaqueta en una imagen propia que contiene el JAR ya compilado y el 
   runtime de Java necesario para ejecutarlo. Esta imagen se construye con 
   un Dockerfile, que es básicamente una receta de pasos: "toma esta base de 
   Java, copia el JAR, expón el puerto 8080, ejecuta la app".

2. MYSQL
   No se dockeriza "tu" MySQL, sino que se usa la imagen oficial de MySQL 
   que Docker descarga automáticamente. Se le indica, mediante variables de 
   entorno, el nombre de la base de datos, usuario y contraseña que va a 
   crear al iniciar. Esto reemplaza el proceso manual de abrir DBeaver y 
   crear la base de datos tú mismo.

3. ORQUESTACIÓN CON DOCKER COMPOSE
   Docker Compose es el archivo que describe "quiero estos dos contenedores 
   corriendo juntos, en esta red, con esta configuración, y que la app 
   espere a que la base de datos esté lista antes de conectarse". Un solo 
   comando (docker-compose up) levanta ambos servicios coordinados.

CÓMO CAMBIA TU FLUJO DE TRABAJO CON DBEAVER:

Esto es importante porque tú vas a seguir usando DBeaver para inspeccionar 
la base de datos, escribir queries de verificación, revisar que los datos 
de auditoría y las boletas se hayan guardado correctamente, etc. Docker no 
reemplaza eso, solo cambia DÓNDE vive el MySQL al que te conectas.

En vez de conectar DBeaver a un MySQL instalado directamente en tu Windows/Mac 
(localhost:3306 con tu instalación normal), vas a conectar DBeaver a un 
MySQL que corre DENTRO de un contenedor Docker, pero que Docker expone hacia 
afuera en ese mismo puerto 3306. Para DBeaver, la diferencia es invisible: 
sigue siendo "localhost:3306, usuario root, contraseña X". La única 
diferencia real es que esa base de datos ahora se levanta y se destruye con 
comandos de Docker en lugar de con el servicio de MySQL de tu sistema 
operativo.

Ventaja práctica: si quieres "resetear" toda la base de datos para repetir 
un test de concurrencia desde cero, en vez de borrar tablas manualmente en 
DBeaver, simplemente destruyes el contenedor y lo vuelves a levantar, y 
Docker recrea la base de datos limpia automáticamente según la configuración 
inicial.

QUÉ NO CAMBIA:

- Tu código Java sigue siendo el mismo, Spring Boot no sabe ni le importa 
  si corre dentro o fuera de un contenedor.
- Tus queries en DBeaver siguen siendo SQL normal de MySQL.
- Tu proceso de testing con JUnit5 no cambia en absoluto.

QUÉ SÍ CAMBIA (Y ES LO QUE SUMA A TU CV):

- Demuestras que entiendes la diferencia entre "funciona en mi máquina" y 
  "funciona en cualquier máquina".
- Demuestras conocimiento de conceptos de DevOps: imágenes, contenedores, 
  redes internas entre servicios, variables de entorno, volúmenes para 
  persistencia de datos.
- El repositorio se vuelve ejecutable por cualquier recruiter o compañero 
  con un solo comando, sin explicaciones adicionales.

ELEMENTOS QUE DEBES PREPARAR (COMO DESARROLLADOR):

1. Un Dockerfile para la aplicación Spring Boot (define cómo se construye 
   la imagen de tu app).
2. Un archivo docker-compose.yml que describa los dos servicios (app y 
   mysql), sus variables de entorno, puertos expuestos, y la dependencia 
   entre ellos (la app debe esperar a que MySQL esté listo).
3. Un volumen de Docker para que los datos de MySQL persistan entre 
   reinicios del contenedor (si no, cada vez que reinicias pierdes todo).
4. Opcionalmente, un archivo de inicialización SQL que Docker ejecute 
   automáticamente la primera vez que crea el contenedor de MySQL, para 
   que las tablas ya existan sin que tengas que crearlas a mano.

CÓMO LO PROBARÍAS COMO TESTER:

- Levantar el entorno completo con Docker y verificar que la app conecta 
  correctamente a MySQL sin configuración manual.
- Apagar y volver a levantar los contenedores, verificando que los datos 
  persisten (gracias al volumen) o se resetean (si eliminas el volumen 
  intencionalmente).
- Conectar DBeaver al MySQL dockerizado y confirmar que ves las mismas 
  tablas, con los mismos datos, que verías en una instalación normal.
- Ejecutar el test de concurrencia de 100 threads contra la instancia 
  dockerizada y confirmar que el comportamiento es idéntico al de MySQL 
  corriendo sin Docker.

9. MECANISMO DE OPTIMISTIC LOCKING (LA SOLUCIÓN)
================================================================================

¿QUÉ ES OPTIMISTIC LOCKING?

Es una estrategia de concurrencia que asume que las colisiones son raras.
En lugar de LOCKEAR la fila (PESSIMISTIC), verificamos si fue modificada.

IMPLEMENTACIÓN EN SPRING JPA:

1. Entidad:
   @Entity
   public class Seat {
       @Version
       private Integer version;  // Spring maneja esto automáticamente
       ...
   }

2. Spring genera SQL:
   UPDATE seats 
   SET status='RESERVED', version=version+1 
   WHERE id=123 AND version=0
   
   (Si version no es 0 → 0 filas afectadas)

3. Si 0 filas:
   Spring lanza: JpaOptimisticLockingFailureException

4. Capturamos excepción:
   @Service
   public class TicketService {
       @Transactional
       public void buySeat(...) {
           try {
               seat.setStatus(RESERVED);
               seatRepository.save(seat);  // Aquí puede fallar
           } catch (JpaOptimisticLockingFailureException e) {
               throw new SeatNotAvailableException("Otro usuario ganó");
           }
       }
   }

VENTAJAS:
✓ No bloquea recursos (DB locks)
✓ Mejor performance bajo alta concurrencia
✓ Detecta cambios entre lectura y escritura
✓ Es estándar en e-commerce

DESVENTAJAS:
✗ Si hay muchas colisiones, el cliente debe reintentar
✗ No garantiza orden de ejecución (first-come != first-served)

PARA NUESTRO CASO: PERFECTO
- Compradores son usuarios humanos (no máquinas)
- Si fallan, pueden elegir otro asiento
- No requiere retry automático

10. FLUJO DE TESTING (CONCURRENCIA)
================================================================================

TEST: 100 usuarios, 10 asientos

SETUP:
1. Limpiar BD (eliminar datos previos)
2. Crear 1 función: "Función Test"
3. Crear 10 asientos: A-1, A-2, ..., A-10 (status=AVAILABLE, version=0)
4. Crear 100 usuarios: user1@test.com, user2@test.com, ..., user100@test.com

EJECUCIÓN:
1. Crear ExecutorService con 100 threads
2. Lanzar 100 solicitudes simultáneamente:
   for i=1 to 100:
      thread[i] → POST /tickets/buy {seatCode: "A-" + ((i % 10) + 1), ...}
   
   Esto hace que todos luchen por los mismos 10 asientos

3. Esperar a que todos terminen (CountDownLatch)

4. Registrar:
   - Cuántos ganaron (successCount)
   - Cuántos perdieron (failureCount)
   - Quién compró qué asiento
   - Mensajes de error

ASSERTIONS:
✓ successCount == 10 (exactamente 10 ganadores)
✓ failureCount == 90 (exactamente 90 perdedores)
✓ DB tickets.size == 10 (10 boletas)
✓ DB seats.status=RESERVED.size == 10 (10 asientos reservados)
✓ Para cada asiento: version == 1 (fue modificado)
✓ No hay dos tickets para el mismo asiento (UNIQUE seat_id)

SALIDA ESPERADA:
```

✅ Usuario 27 compró A-5
```

CU-01: REGISTRARSE

  1. POST /auth/register {email, password, fullName, phone}

CU-02: INICIAR SESIÓN
Precondiciones: Usuario existe
Flujo:
  1. POST /auth/login {email, password}

  3. Validar password (BCrypt.matches)
  4. Generar JWT token
  5. Retornar 200 {token, userId}
Postcondiciones: Cliente tiene token válido

---

CU-03: VER FUNCIONES DISPONIBLES
Precondiciones: Existen funciones en BD

  1. GET /api/functions

CU-04: VER ASIENTOS DE UNA FUNCIÓN
Precondiciones: Función existe, usuario autenticado
Flujo:
  1. GET /api/seats/function/1 (con JWT)
  2. Validar JWT
  3. Buscar asientos con status=AVAILABLE para función 1
  4. Retornar 200 [seat1, seat2, ...]
Postcondiciones: Usuario ve mapa de asientos disponibles

---

CU-05: COMPRAR ENTRADA ★★★ CRITICAL
Precondiciones: 
  - Usuario autenticado
  - Función existe y no está cancelada
  - Asiento existe y está disponible
Flujo:
  1. POST /api/tickets/buy {seatCode, functionId} (con JWT)
  2. Extraer userId del JWT
  3. Validar usuario, función, asiento
  4. Iniciar transacción (@Transactional)
  5. SELECT seat WHERE seatCode=X AND function_id=Y
     (En memoria: seat.version=0, status=AVAILABLE)
  6. Validar status==AVAILABLE
  7. Cambiar status a RESERVED
  8. UPDATE seat SET status='RESERVED', version=1 
     WHERE id=123 AND version=0
     ├─ Si 1 fila: Éxito
     └─ Si 0 filas: OptimisticLockingException
  9. Si falla: Capturar, registrar auditoría, retornar 409
  10. Si éxito:
      - Generar código QR
      - Crear Ticket en BD
      - Registrar en auditoría (RESERVED)
      - Retornar 201 {ticketCode, qrCode, ...}
Postcondiciones: 
  ✓ Boleta creada
  ✓ Asiento reservado
  ✓ Usuario recibe QR
  ✗ Otro usuario recibe error

---

CU-06: VER MIS BOLETAS
Precondiciones: Usuario autenticado, tiene boletas
Flujo:
  1. GET /api/tickets/user/123 (userId en JWT)
  2. SELECT tickets WHERE user_id=123
  3. Retornar 200 [ticket1, ticket2, ...]
Postcondiciones: Usuario ve historial de compras

---

CU-07: VALIDAR ENTRADA EN PUERTA (Admin)
Precondiciones: Usuario admin, boleta existe
Flujo:
  1. Scanner QR → extrae ticketCode
  2. GET /api/tickets/{ticketCode}
  3. Validar ticket.status==ACTIVE
  4. UPDATE ticket SET status='USED', usedAt=NOW()
  5. Permitir entrada
Postcondiciones: Boleta marcada como usada

12. MATRIZ DE DECISIONES ARQUITECTÓNICAS
================================================================================

DECISIÓN 1: Optimistic Locking vs Pessimistic Locking
┌──────────────────────┬──────────────┬──────────────────┐
│ Aspecto              │ Optimistic   │ Pessimistic      │
├──────────────────────┼──────────────┼──────────────────┤
│ Bloqueo en BD        │ No           │ Sí (SELECT...FOR │
│                      │              │ UPDATE)          │
│ Performance alto     │ ✓            │ ✗                │
│ Colisiones raras     │ ✓            │ ✓                │
│ Colisiones frecuentes│ ✗            │ ✓                │
│ Implementación       │ @Version     │ @Lock            │
│ Caso de uso actual   │ PERFECTO     │ Overkill         │
└──────────────────────┴──────────────┴──────────────────┘
ELEGIDO: Optimistic Locking (@Version)
RAZÓN: Venta de entradas es read-heavy, pocas colisiones reales

┌──────────────────────┬──────────────┬──────────────────┐
│ Aspecto              │ Spring Boot  │ Node.js          │

│ Testing              │ ✓ JUnit5     │ ✓ Jest           │
│ Escalabilidad        │ ✓            │ ✓                │
│ Complejidad (este)   │ SIMPLE       │ MÁS COMPLEJO     │

└──────────────────────┴──────────────┴──────────────────┘

DECISIÓN 4: JWT vs Session Cookies
┌──────────────────────┬──────────────┬──────────────────┐
│ Aspecto              │ JWT          │ Session Cookies  │
├──────────────────────┼──────────────┼──────────────────┤
│ Stateless            │ ✓            │ ✗ (estado en BD) │

│ Revocación           │ ✗ Difícil    │ ✓ Inmediata      │

│ Mobile/SPA           │ ✓            │ ✗                │
└──────────────────────┴──────────────┴──────────────────┘
ELEGIDO: JWT
RAZÓN: Stateless, escalable, perfecta para REST API

┌──────────────────────┬──────────────┬──────────────────┐
│ Aspecto              │ Docker       │ Instalación Local│
├──────────────────────┼──────────────┼──────────────────┤

14. RIESGOS IDENTIFICADOS
================================================================================

RIESGO 1: Race Condition en Compra
Probabilidad: ALTA (usuarios concurrentes)
Impacto: CRÍTICO (overbooking)
Mitigación: Optimistic Locking (@Version)
Validación: Test con 100 threads

---

RIESGO 2: Pérdida de Auditoría
Probabilidad: MEDIA (error durante INSERT)
Impacto: MEDIA (debugging difícil)
Mitigación: Try-catch al guardar auditoría, separate transaction
Validación: Test con fallo intencional

---

RIESGO 3: Token JWT Expirado
Probabilidad: MEDIA (usuario espera mucho)
Impacto: BAJA (usuario renueva token)
Mitigación: Expiration=24horas, refresh token (futuro)
Validación: Test de token inválido

---

RIESGO 4: Función Cancelada Mientras Compra
Probabilidad: BAJA (admin raramente cancela)
Impacto: MEDIA (usuario confundido)
Mitigación: Validar function.status antes de compra
Validación: Test CU-05 con función cancelada

---

RIESGO 5: Base de Datos Inaccesible
Probabilidad: BAJA (hosting confiable)
Impacto: CRÍTICO (sistema down)
Mitigación: Connection pooling, retry logic, health checks
Validación: Monitoreo en producción
